# Signals: plain-English watchers over finished runs (P06, slice 1)

The owner writes a signal as a sentence ("session stuck in a loop", "edits tests to pass"). A cheap model reads a digest of each finished run and answers whether the signal fired; a hit is posted and recorded. This slice is the engine: the judge, the daily cap, de-duplication and the precision measure. Not in it: the inbox card, the trigger on finished runs, the replay command.

## Acceptance checks (`tests/Chargehand.Tests/SignalTests.cs`)

| # | Check |
|---|---|
| S1 | A signal the judge says fires is returned and posted once; one it says does not is not. |
| S2 | At most `maxChecksPerDay` judge calls a UTC day across all signals and runs; the rest are skipped and counted; the count resets the next day. |
| S3 | The same signal on the same run fires once. |
| S4 | A judge that throws `SignalException`, or a post that throws, does not stop the other signals. |
| S5 | `ModelSignalJudge` runs the read-only preset, treats the digest as data, and reads `yes <reason>` / `no` (any case); a failed run or empty answer is a `SignalException`. |
| S6 | `SignalPrecision.Of` is hits confirmed / hits labelled, null for none; `Passes` is at least 0.7. |

Value hypothesis: failure patterns found once get watched forever. Cheapest test (owner's): write 3 signals, replay a week of events, hand-label 30 hits, precision at least 70%; it needs the replay command, so it is the next slice.
