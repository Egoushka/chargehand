# Declaring result/v1 and the extension API stable: a checklist for 1.0

> This is a plan for a decision, not the decision. Nothing here freezes anything. The declaration is made by the maintainer after
> 0.9's feedback, in its own pull request, with its own ADR.

**Goal:** When 1.0 is declared, each frozen surface is named, guarded by a test that fails on a breaking change, and described in a
short public text. The maintainer decides when the conditions below are met.

**Spec:** the roadmap's 1.0 line, `docs/adr/0026-extension-model.md` and `docs/adr/0022-error-codes-in-result-v1.md`.

## What "the extension API" means here

Chargehand's extension points are configuration and contracts, not a C# library: `Chargehand.Contracts` is the only published
library; the `Chargehand` package is a tool. The interfaces in `src/Chargehand/` (`IWorkerRuntime`, `IMemoryProvider`, `IEvidenceResolver`,
`IPriceTable`, `ISandbox`, and others) are internal to the tool. Proposed: **the extension API is the profile and preset formats, the
memory and services tool mappings, the secret-source templates, the runtime names and `extensions check`, not the C# interfaces**,
which the declaration says may change in any release. The maintainer confirms this in Task 1 (open question 1).

## Global Constraints

- Public repository rules as in the other plans. No signing keys are created; no release, tag or announcement happens in these tasks.
- A frozen surface changes only additively after 1.0; a removal or meaning change is a 2.0 (`schemas/<name>/v2`, a new `$id`).
- Every frozen surface has a test that fails on a breaking change **before** the declaration is written, not after.

## Surfaces and their guards

| Surface | Files | Frozen means | Guard today | Guard to add |
|---|---|---|---|---|
| `result/v1`, `request/v1`, `run-status/v1`, `task-spec/v1`, `preset/v1` | `schemas/*/v1/*.json`, `src/Chargehand.Contracts/*.cs` | fields, types, enums and required-ness only loosen; new fields optional | `SchemaCompatTests` against the latest `v*` tag; `SchemaFixtureTests` | none for schemas; a test that every enum value in the C# contracts exists in its schema and the reverse |
| Signature semantics | `src/Chargehand.Contracts/ResultSignature.cs`, ADR 0036 | ES256, RFC 8785 canonical form, `key_id` derivation, "minus `signature`" | `ResultSignatureTests` | checked-in test vectors (a signature over a fixed result made with a fixed public test key **embedded in the test as text**, generated by the test at run time and never a file) so a canonicalisation change is caught, plus the RFC 8785 examples |
| `Chargehand.Contracts` public API | `src/Chargehand.Contracts/` | public types and members remain; new ones may be added | none | a public-API snapshot test (reflection over the assembly, compared to a checked-in text listing; additions allowed, removals fail) |
| Error codes and `retryable` | ADR 0022, `ChargehandException.cs` | codes keep their meaning; new codes additive | tests per code | a test listing every code in the schema's enum against a documented table in `docs/guide/reference.md` |
| Profile format and defaults | `docs/guide/reference.md`, `src/Chargehand/Config/` | keys keep meaning and defaults; unknown-key behaviour documented; removals only with a migration message for one minor before 1.0, none after | load tests | a golden-profile test: a checked-in profile using every key loads and yields expected values; documentation-versus-code test that every key in the reference table is read by the loader |
| Memory and services mappings, secret templates | ADR 0034, `docs/guide/memory-and-services.md` | placeholders, mapping fields and `{secret:item}` | `ExtensionsCheckTests`, mapping tests | golden mapping test with every placeholder |
| CLI commands, flags and exit codes | `docs/guide/reference.md`, `src/Chargehand.Cli/` | commands and exit codes in the reference | per-command tests | a test that parses the reference's command table and runs `--help` for each (listed flags exist); exit codes asserted per command |
| MCP tool `orchestrate` and HTTP `/v1/*` | `docs/mcp-server-2025-12-11.schema.json`, `docs/guide/mcp.md`, `docs/guide/server.md` | tool name, input schema, HTTP paths and status codes | `McpServer` and HTTP tests | a snapshot of the tool's input schema and of the route table; additive only |
| Output text of `verify`, `extensions check` | the reference | **not frozen**: exit codes only | — | say so in the declaration |

## Tasks

Each is small enough for one pull request. Order: 1, then 2 to 5 in any order, then 6, then 7 once the feedback conditions hold.

### Task 1: Decide the scope

- [ ] Maintainer confirms or changes "What the extension API means here" and the table's rows (open question 1). Record the answer in
  ADR 0038 as `proposed` with the surfaces listed. Files: `docs/adr/0038-stability-and-compatibility-policy.md`, `docs/guide/decisions.md`.
  Include the deprecation policy: a surface deprecated in a minor keeps working for at least two more minors; the changelog says
  "deprecated" and names the replacement.

### Task 2: Additive-only guards for contracts

- [ ] Failing tests first: enum parity (C# to schema); a public-API snapshot of `Chargehand.Contracts`; checked-in signature test vectors
  generated in-test. Files: `tests/Chargehand.Tests/ContractParityTests.cs`, `PublicApiSnapshotTests.cs`, `tests/Chargehand.Tests/public-api/Chargehand.Contracts.txt`.
- [ ] Also extend `SchemaCompatTests` so the comparison base is the latest `v*` tag **and** `v1.0.0` once it exists. `scripts/check.sh` green.

### Task 3: Guards for profile, presets and mappings

- [ ] Golden profile with every key and a documentation-versus-loader test; golden mapping test with every placeholder. Files: `tests/Chargehand.Tests/GoldenProfileTests.cs`, `tests/Chargehand.Tests/golden/profile.full.json`.
  The golden file uses placeholders only (no real hosts or secrets).

### Task 4: Guards for CLI, MCP and HTTP

- [ ] Reference-table-versus-`--help` test; exit codes per command; snapshot of the MCP tool input schema and the HTTP route table. Files: `tests/Chargehand.Tests/CliSurfaceTests.cs`, `McpSurfaceTests.cs`, snapshots beside them.

### Task 5: Error code table

- [ ] Every enum value of `error.code` documented in `docs/guide/reference.md` with its `retryable` and `action` meaning; a test that the two lists match.

### Task 6: The stability text

- [ ] Write `docs/guide/stability.md` (what is frozen, what is not, how a change is made, the deprecation policy, how to report a break) and a draft of the
  declaration below, as a file under `docs/plans/` only. No README, ROADMAP or CHANGELOG change in this task.

### Task 7: The declaration (maintainer, after the conditions below)

- [ ] ADR 0038 to `accepted`; `docs/guide/stability.md` linked from the README and guide index; `ROADMAP.md` 1.0 ticked; `Directory.Build.props` set to `1.0.0`; changelog entry; the release
  by the release checklist, with the `release` environment approved by the maintainer. **Not done by any agent.**

## Draft declaration text (for the maintainer to edit; not published)

> chargehand 1.0 declares these stable: the JSON schemas `result/v1`, `request/v1`, `run-status/v1`, `task-spec/v1` and `preset/v1` and
> the `Chargehand.Contracts` package's public API; result signatures (ES256 over the RFC 8785 form); the profile and preset formats,
> the memory and services mappings and secret templates; the CLI's commands, flags and exit codes; the `orchestrate` MCP tool's input
> and the HTTP `/v1` routes; the error codes. Stable means: after 1.0 they change only by adding optional things. A removal or a
> change of meaning waits for 2.0 and its own schema major. Not stable: the C# types inside the `Chargehand` tool package, the text
> of messages and command output, the run log's format, prompts, and anything marked experimental in the guide. A surface is
> deprecated for at least two minor versions before it is removed in a major. Report a break as an issue labelled `compat`.

## Feedback from 0.9 needed before the declaration

The declaration is not made until each of these has an answer, written down in the ADR:

1. **Outside use.** At least five outside people have used chargehand (the 0.9 exit) and at least one program other than chargehand's own
   code consumes `result/v1` (through `Chargehand.Contracts` or raw JSON). Where: issues, discussions, nuget download counts, stars.
2. **What they asked to change.** Every issue or comment about a contract, profile key, flag or error code, triaged as *needs a break*,
   *additive*, or *no change*. Any *needs a break* is done before 1.0, not after.
3. **The `support` field in practice.** The benchmark's audit (Task 7 of the benchmark plan) shows whether `partial` and `unsupported` mean
   what the guide says; if the judge's verdicts are redefined, that happens before the freeze.
4. **The signature in practice.** At least one third party verified a signed result with `chargehand verify` or `ResultSignature.Verify`
   without help, or the feedback names what blocked them.
5. **The extension surface.** At least one profile or preset written by someone other than the maintainer, and every place it needed
   help recorded as a documentation fix or a change.
6. **No open `broken` item touching a frozen surface.**

## Open questions for the maintainer

1. Is the extension API the configuration surface (proposed) or also selected C# interfaces?
2. Is the deprecation window of two minors right for a one-maintainer project, or should it be shorter?
3. Should `profile/v1` get a JSON Schema so the profile has a machine-checked contract like the others? (Not done in this plan; it would be a 0.9.x addition.)
4. Are there outside consumers to wait for, or is "five outside people" enough?
