Driven sessions ([ADR 0039](../adr/0039-driven-writing-sessions.md)) run a list of tasks as headless Claude Code sessions, one container each, following the [`change` skill](change.md), and end each in a pushed branch `chargehand/<run>` and a **draft** pull request. By default chargehand never merges and never enables auto-merge; on the repositories the profile opts in ([ADR 0046](../adr/0046-integrator-and-ci-fixer.md), "Merging by policy" below) it marks the pull request ready and merges it only through the repository's own required checks. **Status: a request with a `driven` block runs the batch, and `scripts/driven-e2e.sh` has run it with a real model on synthetic repositories and on a real TypeScript-on-Node repository; it is deployed on one VPS and has run there once, to a draft pull request; on the subscription the real model credential stays in the batch's egress container and a session holds a per-task token** (see "The model credential"). Keep `driven.enabled` false in a shared profile.

## How a task is isolated

- **One container per task**, started from one fixed template ([`ContainerTemplate`](../../src/Chargehand.Driven/Containers/ContainerTemplate.cs)): non-root, read-only root filesystem, no capabilities, `no-new-privileges`, memory, CPU and process limits, one internal network, two named volumes, no Docker socket, no host mount. No value in a request can add a flag, a mount, a network mode or a capability.
- **No route out.** The container sits on an `--internal` Docker network. One egress container per batch is on that network and on an outside one and forwards only TLS connections to an allowlist (port 443, named hosts, and never a name that resolves to a private address). A process that ignores its proxy variables still cannot get out. The proxy sees host names, not content, so an allowlisted registry can still receive data in a URL.
- **The server never holds the Docker socket.** A [runner service](server.md#runner-driven-sessions) does, behind a narrow API. The runner starts only images on its allowlist, by digest, and touches only containers, volumes and networks that carry chargehand's label or prefix. The task and the results move through a session's output volume by a helper container with no network, started from the same image, that writes only `task.json` (and `seed.bundle` for a continuation, ADR 0044) and reads only the bundle, the report and the outcome. It is still a root-equivalent socket on a rootful engine, which is the security cost of this design.
- **A session calls chargehand back** (research, review) with a run-scoped token, through a forward the batch's egress container carries; the token opens only the presets `default` and `review` on its task's repository and commit, within the task's caps ([run tokens](server.md#run-tokens-driven-sessions)).
- **The model credential is not in a session container in subscription mode** (`credential_delivery: gateway` in the batch result). The batch's egress container also serves a plain-HTTP model endpoint (port 3129) on the internal network. The session gets `ANTHROPIC_BASE_URL` pointing at it and, as `CLAUDE_CODE_OAUTH_TOKEN`, a per-task token the host signed (HMAC, naming the run, an expiry and the task's token cap). The endpoint accepts only such a token (anything else: 401), swaps it for the real credential, forwards the request over TLS to one configured host (`api.anthropic.com`; no redirect is followed, only `/v1/...` paths, only to public addresses), and streams the response back. It counts input plus output tokens from the streamed `usage` and refuses a run past its cap (403). It logs only run id, status and token counts, never a header value or a body. **What this costs:** the real credential now lives in the egress container, as an environment variable from an env file the host writes (mode 0600, deleted after the start). That container is chargehand's own image running only the proxy and the endpoint, with no mounted workspace and no repository code, but it is a process that holds the credential, and `docker inspect` on the engine shows it. A leaked per-task token is worthless outside its run and its internal network. In **API-key mode** the real key is still the session container's environment (`credential_delivery: environment`): the exchange is untested with a key. An engine reached through the runner service also still gets `environment`: the runner's egress call does not carry the credential.
- **The credential that pushes is never in a container.** chargehand fetches the session's bundle into a scratch clone of its own checkout, checks the branch, and pushes from there.

A session's and the verification run's `/tmp` is a `noexec` tmpfs, so a repository whose tests write a script there and run it fail with `EACCES`. The template stays as it is; the repository names a directory under `/work` instead, in its verification command: `context.verify: ["sh","-c","mkdir -p /work/.tmp && export TMPDIR=/work/.tmp && npm ci && scripts/check.sh"]`. Measured on a TypeScript-on-Node repository: 3 of 217 tests failed on `spawn ... EACCES` with the default `/tmp`, 0 with `TMPDIR` in `/work`.

A .NET repository needs no extra image: the session image is built on the .NET 10 SDK (its size is unchanged by this note), and `DOTNET_CLI_HOME` (`/work/.dotnet`) and `NUGET_PACKAGES` (`/work/.nuget/packages`) point at the volume, so a restore does not fill the tmpfs at `/home/session`. A restore needs the network: add `api.nuget.org` and `globalcdn.nuget.org` (the package CDN `api.nuget.org` may redirect to) to the profile's `driven.network.allow`; a repository with a private feed adds that host too. Verification command for a repository with a solution at the root: `context.verify: ["sh","-c","mkdir -p /work/.tmp && export TMPDIR=/work/.tmp && dotnet test --nologo"]`. An SDK newer than the image's (`global.json` with `rollForward: disable` on another feature band) fails the restore; the image carries the latest 10.0 SDK at build time.

## What happens after a session

chargehand checks the branch itself and pushes only if every check passes:

| check | refused with |
|---|---|
| the session made a bundle | `session_failed` |
| the branch descends from the base commit and changes something | `session_failed` |
| the diff carries no secret-shaped text, none of the credentials the session had, no secret-like file names | `session_failed`, naming the kind and the path, never the value |
| the diff changes no CI configuration (`.github/workflows`, `.gitlab-ci.yml`, ...) unless allowed, because pushing such a branch can run it with the repository's secrets | `session_failed` |
| the repository's tests pass in a **fresh** container on the bundle's branch (chargehand's own run; the session's claim is kept apart) | `verification_failed`; a repository with no test command is not pushed unless allowed |
| the push of `chargehand/<run>` (one ref, never forced) is accepted by a credential that cannot push the default branch | `push_rejected` |
| the draft pull request opens | `pr_failed`, with the pushed branch named |

A green draft pull request is evidence that a command passed in a container, not that the change is right. The session can still edit the tests or the build script so the command passes; the `verification` artifact lists those paths. When every changed path is a test, fixture, snapshot or build file (`scripts/`, `Makefile`, `package.json` as a whole, project and solution files, CI configuration) and the task's goal does not mention test, spec, build, CI, coverage, fixture or snapshot work, the result is flagged: the `verification` artifact gets `test_integrity` (`flagged`, `reason`, `test_paths`, `build_paths`; null otherwise), the result summary and the task detail say so, the pull request body starts with a warning, and the integrator treats the pull request like `ask` whatever the policy says: it marks it ready, comments why and never merges it. A goal that asks for tests is not flagged. The check is path rules plus a word list, so it is a warning for a reader, not proof.

## Merging by policy

[ADR 0046](../adr/0046-integrator-and-ci-fixer.md). Off unless the profile has a `driven.integrator` block; with none, a task ends in a draft pull request and chargehand never touches it again. With one, chargehand acts on a finished task's pull request **as a GitHub App**, not with the push credential (which bypasses rulesets and so cannot enforce a policy). The App's JWT (RS256, signed with the key from the secret store) is exchanged for an installation token that is kept until shortly before it expires.

| `driven.integrator.repositories["owner/repo"]` | what happens to the task's pull request |
|---|---|
| not listed | nothing: the draft is left alone |
| `ask` | marked ready for review, one comment that the policy is ask, no merge |
| `merge` | if behind its base, the branch is updated (`update-branch`); marked ready; then auto-merge with squash, pinned to the head commit, so GitHub merges once every required check and rule passes; if GitHub already calls it mergeable, a squash merge pinned the same way; on a conflict, one comment and no merge |

`always_ask` is a list of repositories that are `ask` whatever else says, even one that `repositories` calls `merge` or does not list: put a repository whose merge deploys something there. A `[partial]` pull request is never touched. chargehand never bypasses a rule: it has no admin bypass and the App should not be on any ruleset's bypass list, so a ruleset that requires a review still waits for a person. A repository with no required checks merges as soon as GitHub calls it clean; list it as `merge` only after its rulesets require the checks that should gate it. The pull request's body says which of these applies.

**CI fixer.** On a listed repository, chargehand then watches the pull request's required checks (every 30 s, for `ci_fix.wait_minutes`, default 20, and the task keeps its slot meanwhile). When one fails and none is still running, it starts a short session on the same branch, seeded from the last bundle, whose goal names the failing jobs and carries the end of each job's log (fetched with the App token; given as data). The session's fix goes through the same handover as any branch (secret scan, no CI configuration, chargehand's own tests, an ordinary push of the same branch), and the pull request updates. At most 3 attempts per pull request, never twice for the same failing jobs, `ci_fix.max_turns` (20) and `ci_fix.max_minutes` (15) each, and its spend counts toward the task's caps. The count lives on the pull request, in a hidden marker in the comment chargehand posts before each attempt, so a restart or a second batch cannot exceed it. When attempts run out, or the same jobs fail again, chargehand comments once and leaves the pull request to a person. `ci_fix.max_attempts: 0` turns the fixer off.

The App needs contents and pull requests write, checks, actions and commit statuses read, and nothing else (Issues read and write too, if [GitHub intake](intake.md) is on): no administration, no workflows, no webhook, and installation on only the repositories chargehand may merge into. Profile:

```json
{ "driven": { "integrator": {
  "app_id": 123456, "installation_id": 7654321, "private_key_secret": "chargehand-app-key",
  "repositories": { "owner/library": "merge", "owner/service": "ask" },
  "always_ask": ["owner/infrastructure"],
  "ci_fix": { "max_attempts": 3, "max_turns": 20, "max_minutes": 15, "wait_minutes": 20 } } } }
```

Not run against GitHub yet: the calls are checked against a fake host and recorded request shapes. The open points (rulesets and `isRequired`, `update-branch` on a draft, the job-log id) are listed in the ADR, and each fails without merging.

### GitLab

A remote on GitLab gets a merge request where GitHub gets a pull request, and the same policy and CI fixer work through it ([ADR 0047](../adr/0047-core-and-driven-assemblies.md), the forge extension point). The forge is read from the remote URL: `gitlab.com` and a host whose first label is `gitlab` (`gitlab.example.test`) are GitLab, any other host is GitHub as before. For anything else set `driven.forge.kind` (`github` or `gitlab`); it applies to every remote of the profile. Remotes are `https://host/group/sub/project.git`, `git@host:group/sub/project.git` or `ssh://git@host/group/sub/project.git`; the namespace can nest, and `driven.integrator.repositories` and `always_ask` name a project by its whole path (`group/sub/project`). The API root is `https://<remote host>/api/v4/`; `driven.forge.base_url` replaces it (the instance root or the API root, https only), for a host behind a path or another name.

```json
{ "driven": {
  "push_secret": "gitlab-token",
  "forge": { "kind": "gitlab", "base_url": "https://git.example.test", "token_secret": "gitlab-api-token" },
  "integrator": { "repositories": { "group/sub/project": "merge" } } } }
```

One token does everything, sent as `PRIVATE-TOKEN`; there is no App. It is `driven.forge.token_secret`, else `driven.push_secret`, which also pushes the branch over https, so that token then needs the `api` and `write_repository` scopes. Use a project or group access token (or a bot user's) that cannot push the protected default branch; the project's merge rules still decide what it may merge. `driven.integrator` needs no `app_id`, `installation_id` or `private_key_secret` for a GitLab-only profile (the three are all set or all left out).

| chargehand does | GitLab call |
|---|---|
| open a draft | `POST /projects/:id/merge_requests`, the title prefixed `Draft: `; a request that already exists for the branch is found by `GET /merge_requests?source_branch=&state=opened` |
| edit the title and body | `PUT /merge_requests/:iid` with `title` (kept a draft if it is one) and `description`; GitHub: `PATCH /repos/:o/:r/pulls/:n` |
| read the state | `GET /merge_requests/:iid` (`state`, `draft`, `sha`, `detailed_merge_status`, `head_pipeline`), `GET /pipelines/:id/jobs`, `GET /merge_requests/:iid/notes` (last 50) |
| how far behind | `GET /repository/compare?from=<branch>&to=<base>`: the commits of the base the branch lacks |
| update the branch | `PUT /merge_requests/:iid/rebase`, after checking that the head is the one expected |
| mark ready | `PUT /merge_requests/:iid` with the title less its `Draft:`, `[Draft]` or `(Draft)` prefix |
| auto-merge | `PUT /merge_requests/:iid/merge` with `merge_when_pipeline_succeeds: true`, `sha` (the head) and `squash: true` |
| merge now | the same without `merge_when_pipeline_succeeds` |
| comment | `POST /merge_requests/:iid/notes` |
| a failing job's log | `GET /jobs/:id/trace`, the end of it, colour codes and section markers removed |

**"Required checks" on GitLab.** GitLab names no individual required check; its gate is "pipelines must succeed" (and approvals, discussions and the like). chargehand reads the jobs of the merge request's head pipeline and counts every job that is not `allow_failure` as required: `success` and `skipped` pass, `failed` fails, `created`, `pending`, `running`, `preparing`, `scheduled` and `waiting_for_resource` are pending, and `canceled` or a `manual` job that blocks ends the wait as "waiting for a person". A pipeline that belongs to an older head is ignored (a fresh head has no checks until GitLab creates its pipeline), and a pipeline that ended with no job at all, as a broken `.gitlab-ci.yml` does, is one required check named `pipeline`. `detailed_merge_status` is mapped onto the words the integrator reads: `mergeable` is clean, `conflict` is dirty, `need_rebase` is behind, `draft_status` is draft, `checking` and `unchecked` are unknown, and everything else (a pipeline still running or missing, approvals, open discussions, a blocking rule) is blocked, which makes chargehand ask for auto-merge.

Limits, all of which stop short of a merge:

- Only the first 100 jobs of the pipeline are read, and jobs of child or downstream pipelines are not. A failing downstream pipeline still blocks GitLab's own merge, but the CI fixer does not see it.
- `merge_when_pipeline_succeeds` is the parameter GitLab deprecated in favour of `auto_merge`; it still works in API v4. GitLab may refuse it while the merge request has no pipeline yet (UNKNOWN: not checked against an instance), for instance when chargehand asks before the pipeline of a fresh push exists; the integrator then stops with GitLab's refusal and a person merges.
- GitLab's rebase takes no expected head and rewrites the branch's commits. A CI fix session seeded from the bundle made before the rebase pushes a branch that no longer fast-forwards the remote, and chargehand never forces; that attempt is reported as pushing nothing.
- The calls are tested against a fake host only, like GitHub's: not run against a GitLab instance. The `Draft:` title (rather than a `draft` attribute) and the rebase path are the points to check first on a real one.

## Watching a batch

While a batch runs, its own run (`GET /v1/runs/{batch}`, a `202` with `run-status/v1`, and `GET /v1/runs/{batch}/events`) carries each task's steps, every event with `task_id` and a `detail` line such as `task t1: 48200 tokens, 12 turns, stage write`:

| Event | When | Fields |
|---|---|---|
| `container_started` | the task's session container is up | |
| `session_progress` | the session's tally changed since the last poll (every 5 s) | `tokens` (input plus output so far), `turns` (assistant messages), `stage` (`research`, `write`, `test` or `review`: the step of the latest tool call that names one, the order `chargehand runs adherence` checks), `cache_read` and `cache_write` (cache tokens so far), `usd_estimate` (the session's dollar equivalent so far, see below) |
| `verify_finished` | chargehand's own test run ended, pass or fail | |
| `pushed` | the branch is pushed | `branch` |
| `pr_opened` | the draft pull request is open | `pr_url` |
| `task_finished` | the task ended, after the batch's caps had their say | `branch` and `pr_url` when there are some, `tokens` in all; `detail` names the state |
| `governor` | one per decision the session's governor logged (below), published when the session ends | `detail`: mode, action, signal, rule, turn, and spend against the budget when priced |
| `integrated` | a step of the integrator on an opted-in repository (below): marked ready, branch updated, auto-merge enabled, merged, a CI fix attempt started or pushed, or why it stopped | `detail`; `pr_url` and `branch` |
| `question` | a session ended with a question for a person (`needs_input`), published when the session ends, before the handover ([answering a question](#answering-a-question)) | `detail`: `task t1: the session asked:` and one `- <question>` line each |
| `plan` | the planning step ended, before any task starts ([planning a batch](#planning-a-batch)) | `detail`: one line, each task's size, chains and assigned numbers, and what the planner read; or `plan skipped:` and why |

A task's own run id is known only when it ends, so `GET /v1/runs/{task}` is `404` until then; follow the batch. `turns` and `stage` come from the session image's driver: an image built before they existed reports `tokens` only, and one built before `cache_read`, `cache_write` and `usd_estimate` omits those.

**Spend, live.** The driver reads each assistant message's `usage` (input, output, cache read, cache creation) and model, and keeps running totals. With the profile's price table (`prices`, passed to the session in `task.json`) it prices them model by model, cache reads at the model's cache-read rate, and writes `usd_estimate` beside `cache_read` and `cache_write` in `session-usage.json`. It is a dollar equivalent, not a bill: it exists on a subscription too, where `usd` stays unknown. It is null (never 0) when the profile has no prices or no message could be priced; when only some could, it sums those and `usd_estimate_partial` is true. It caps nothing, and Claude Code's own `total_cost_usd` arrives only with the final result. A session image built before this change writes none of these fields; the host and the image move together, so rebuild the image with the host.

From a terminal, or from a Claude Code session's Monitor tool, `chargehand watch <run-id>` prints one line per event (`pr_opened: task t1: draft pull request opened https://...`) and ends with `run_finished: <status>: <summary>`. The exit code is the batch's: 0 completed, 1 failed, denied or lost, 3 needs input, 2 a wrong key or an unknown run. `session_progress` is thinned to one line per 30 s per task unless the stage changes, and a dropped connection resumes without repeating lines. The server is `--url` or `CHARGEHAND_URL`, the key `CHARGEHAND_API_KEY`; a missing one comes from the profile's `http` block. `chargehand cancel <run-id>` asks the server to cancel (the same as `POST /v1/runs/{id}/cancel`); stopping `watch` does not cancel the run.

### From a Claude Code session

`/chargehand:run <prompt>` (the plugin's `run` skill) hands a prompt to a one-task batch on the connected chargehand server and only observes it: it builds the request (preset `driven`, the session's repository root and `HEAD`, one task whose goal is the prompt), gets the run id from the call that returns after 10 s, then runs `chargehand watch <run-id>` under the Monitor tool and passes on the milestones, ending with the draft pull request. The skill pre-approves `orchestrate`, `Monitor`, `chargehand watch|show|cancel` and two read-only git commands; Claude Code still asks for anything else, and the skill tells the session not to do the task itself. It needs a server that runs driven sessions and can read the repository (the plugin's own stdio server cannot), the `chargehand` command on `PATH`, and `CHARGEHAND_URL` and `CHARGEHAND_API_KEY` in the shell Claude Code runs in. A session works from the committed `HEAD`, not from the working tree. With `driven.enabled` false the call fails with `driven sessions are off in this profile` and the skill says so.

## The result

Each task has its own `result/v1` under its own run id (`GET /v1/runs/{id}`); the batch result lists them. Its claims are the session's, cited against the pushed commit and put through the same evidence resolver and [support check](support-and-signing.md) as any result. Artifacts: `branch`, `pull-request`, `verification` (chargehand's run), `session-tests` (the session's claim), `review` (the nested runs), `session-log` (a reference and a hash, never inline), `governor-log` (the same, for `governor.jsonl`, when a governor ran). A task whose branch was fetched and changes something also has `changes` (below). A batch is `completed` only when every task ended in a draft pull request; otherwise it is `failed` with `tasks_incomplete` naming the tasks that did not. A batch the caller cancelled (`POST /v1/runs/{id}/cancel`, `POST /v1/halt`) before it finished is `failed` with `cancelled` and the summary `cancelled by the caller: N of M tasks finished`; tasks that finished keep their outcome in the `driven-batch` artifact, running ones are `cancelled` and ones not yet started are `not_started` with error code `cancelled`.

### The `changes` artifact

What the branch changes against its base, from chargehand's own clone of the bundle (`application/vnd.chargehand.changes+json`, inline). It is there whether or not the branch was pushed, so a refused task shows what it would have pushed.

| Field | |
|---|---|
| `base`, `commit` | the commit the session started from and the branch commit |
| `files` | `{path, added, removed, binary}` per path, from `git diff --numstat --no-renames`: a rename is a delete and an add; a binary file has `added` and `removed` null |
| `files_total` | the number of changed paths, even when `files` is cut |
| `diff` | the unified diff (`git diff base commit`, three lines of context), cut at a line within 32 KiB; null when the diff looked like it carried a secret (the paths and counts stay) or when it did not fit |
| `diff_truncated` | true when `diff` is cut or left out |

An inline artifact holds at most 64 KiB: if the whole does not fit, the diff is left out first, then paths from the end of `files`. For the full diff, fetch the pushed branch.

## Tracing a batch

With the profile's `telemetry` block, a batch reaches the same Langfuse project as an orchestrator run ([ADR 0042](../adr/0042-driven-session-telemetry.md)), under the `trace_id` that the batch's `result/v1` and every task's carry:

```
chargehand.driven.run       run id, preset, repository, base commit, task count, credential delivery, status, error code, pull-request links, tokens
└─ chargehand.driven.task   one per task: task id, its run id, state, error code, branch, pull-request URL, model, Claude Code session id, turns, tokens, wall seconds
   └─ chargehand.driven.session   the session as one generation, container start to end: model, session id, and with usage_on_spans its usage and cost
```

A task that did not complete has error status on its span, and so does a batch that did not. On a subscription no gateway records the session's calls, so set `telemetry.usage_on_spans` ([ADR 0021](../adr/0021-usage-on-spans-without-a-gateway.md)): the session span then carries `usage_details` (input, output, cache read, cache write, summed over the models the session called) and `cost_details` from the profile's price table, model by model. The table may key a model under any provider (`provider/claude-sonnet-5-5` prices Claude Code's `claude-sonnet-5-5`); a model with no price leaves the cost unknown rather than zero. Claude Code's own list-price figure is beside it as `chargehand.claude_code.cost_usd`. Usage arrives when a session ends; while it runs, tokens are on the run's events.

### Claude Code's own telemetry

`driven.network.otlp_url` (`http://host:port` of an OTLP/HTTP collector as the egress container reaches it) turns on Claude Code's own export of logs and metrics from each session container: `CLAUDE_CODE_ENABLE_TELEMETRY=1`, OTLP over `http/protobuf`, cumulative metrics, and `OTEL_RESOURCE_ATTRIBUTES` with `chargehand.run_id` (the batch), `chargehand.task_id`, `chargehand.task_run_id` and `chargehand.trace_id`. It goes through a forward on the egress container, so its port must differ from `mcp_forward`'s and `model_url`'s. User prompts are not logged (`OTEL_LOG_USER_PROMPTS` is never set), no header is set, so the collector must accept the session unauthenticated on that network, and no traces are exported. Claude Code's events carry `session.id`, the value on the task span's `chargehand.claude_code.session_id`. An `https` collector, credentials or a query in the URL, or a port another forward uses is refused before anything is created.

```json
"driven": { "network": { "otlp_url": "http://collector-host:4318" } }
```

## Limits and the kill switch

`max_parallel` (default 2, never above 4), and two ceilings because a subscription has no dollar price: a **token** ceiling that binds in both credential modes, and a **dollar** ceiling that binds with an API key. A batch starts no task it could not afford, and stops running tasks that overshoot its cap by more than one task's cap. A task whose session ended on a usage or rate limit (the result says "usage limit" or "rate limit", or names a 429 as an HTTP status) ends `rate_limited` (retryable) instead of `session_failed`, and the batch holds new starts until the limit lifts: the reset time when the result prints one (`...limit reached|<unix seconds>`), never less than 15 minutes (also the wait when none is printed or it is already past). Running tasks go on. Two such endings in a row with no task finishing between them, or a reset more than 6 hours away, end the batch `failed` with the retryable `rate_limited` error, the tasks not started reported `not_started`; resend them after the reset. An unavailable subscription stops new starts and says how to switch the profile to an API key; nothing switches on its own. Not yet classified: a 429 the egress gateway sees while Claude Code retries inside a session, and result wordings with a reset time but no pipe (they get the 15-minute wait). Every session also ends on no progress, a repeated identical tool call, too many turns, or a wall clock.

**Admission by free memory and load ([ADR 0045](../adr/0045-governed-sessions.md)).** `max_parallel` counts tasks; it does not know the host. Six sessions at a 4 GiB memory limit are 24 GiB, and a server with 2 GiB free kills them or starves its other tenants. So a task also waits until the host has room: available memory (`MemAvailable` in `/proc/meminfo`, the runner's `GET /host`, or this machine's `/proc` without a runner) minus `driven.admission.reserve_mb` (default 1024) must cover the task's `memory_mb`. Containers started in the last 60 seconds count at their whole limit, because the host's figure does not show their growth yet, so a burst of starts cannot all see the same free memory. `driven.admission.max_load_per_cpu` (default unset: no load rule) also holds new starts while the one-minute load average per processor is above it. A waiting task looks again every 5 seconds; a running task is never stopped for memory or load. A task that waits has one `session_progress` event, `task t2: waiting for memory (2210 MiB available, 1024 reserved, 4096 needed)`. To keep a batch from waiting forever on memory that only other tenants hold, a task is admitted anyway when nothing of this server is running, and its event says `admitted with nothing else running, though memory is short (...)`. A host that cannot say (a runner older than `GET /host`, which answers 404; a machine with no `/proc/meminfo`, such as macOS) leaves admission off: tasks start by count as before and the server log says so once. Each session container also gets swap equal to its memory limit (`--memory-swap` at twice `--memory`).

```json
{ "driven": { "admission": { "reserve_mb": 2048, "max_load_per_cpu": 1.5 } } }
```

**Where the limits live.** A session's operational limits (`max_minutes`, `no_progress_minutes`, `max_turns`, `max_tokens`, `memory_mb`, `cpus`, `pids`) have defaults in `presets/driven.yaml`, and the profile's `driven.limits` block overrides them key by key; a key left out keeps the preset's value. The reason is [Prompt CI](prompt-ci.md): the `driven/session` cell gates `presets/driven.yaml`, so any edit of the file needs the owner's approval and a model-backed run of up to two hours, a price that does not fit a change of a wall clock or a memory size. The preset keeps what Prompt CI evaluates (the node kind's model, permissions and budget) and the egress allowlist; add hosts with `driven.network.allow`. `driven.limits` is checked when the profile loads against the container's bounds (`memory_mb` 256 to 65536, `cpus` 0.1 to 32, `pids` 16 to 4096, the rest at least 1). It applies to batches that start after the server restarts; a resumed batch takes the values in force then.

```json
{ "driven": { "limits": { "max_minutes": 90, "max_turns": 200, "memory_mb": 8192 } } }
```

**The governor ([ADR 0045](../adr/0045-governed-sessions.md)).** The driver in each session runs a governor that reads the stream and decides, with no model call, when the session is stuck or over budget. Stuck signals: the same tool call with the same output 4 times in a row (`repeated_call`), one identical action failing 3 times (`repeated_failure`), A-B-A-B-A-B (`alternation`), 8 failing calls in a row (`failing_calls`), more than 10 commands that only ask what the container has (`environment_probing`: `which`, `--version`, `uname`, `ls /usr`, ...), and the diff against the base commit (tracked files, added plus removed lines, measured every 30 s when a turn has passed) unchanged for 40 turns (`no_diff_growth`). The first hit of a signal is a `warn`; the same signal again 10 or more turns later, or a second signal while one is warned, is a `checkpoint`. A message whose context (input, cache read, cache write) passes 160,000 tokens is a checkpoint, and so is spend at 85% of the task's budget; 100% is a `stop`. Commands that wait on purpose (`sleep`, `--watch`, `gh run watch`) count toward no rule. Spend is `usd_estimate` plus what the task's earlier sessions spent; the budget is the request's `tasks[].budget_usd`, else the flat budget of its `size` (S, M or L, default M: 1.5, 4 and 10 dollar equivalents, overridable in `driven.governor.budgets`). Without a price table there is no spend rule. Every decision goes to `governor.jsonl` in the output volume (secrets redacted, values cut at 200 characters), the outcome file carries the first 50, the task result has a `governor-log` artifact and the run has `governor` events. In the default `observe` mode nothing is stopped, and no warning reaches the session in any mode. The log is what tells whether the rules stop good work before `enforce` acts. `driven.governor` in the profile sets `mode` (`observe`, `enforce` or `off`) and every threshold; it needs a session image built from this release (an older one ignores it).

**Enforce mode and the handoff.** With `mode: enforce` the driver acts: a checkpoint ends the session as a stall with reason `checkpoint_stuck` (any stuck signal), `checkpoint_context` or `checkpoint_spend`, and 100% of the budget ends it with `budget_spent`. The decision that stopped the session is logged with `acted: true`; warns stay log-only. The three checkpoint reasons continue like `turn_limit` (a fresh session on the same branch, within `max_continuations`); `budget_spent` does not, and a stop with commits is handed over as a `[partial]` draft pull request. `observe` still acts on nothing.

On every stop the driver makes (any stall, the token cap and the governor's), after the snapshot commit, it writes `handoff.json` and `progress.md` (at most 16 KiB) to the output volume. They are built from git and the stream with no model call: the commit the workspace started at and the branch's head, commit subjects, changed paths with added and removed lines, the last test command with its exit code, the `change` skill's steps (research, write, test, review) each with a `passes` flag that is true when the step's latest tool call returned without an error, the session's own todo list, and its last 60 tool calls as name and arguments, outputs removed. Each item is redacted with the session's secrets and scanned for token and key patterns; an item that matches is dropped and listed as a finding by pattern name only. A continuation's prompt carries `progress.md` (cut to 8,000 characters) and says the earlier commits are offered, not required: if the handoff shows the approach failed, the session may reset to the base commit. A `[partial]` pull request body carries it too (cut to 6,000). The server reads the two files as optional: a runner older than this release refuses their names and the task goes on without them.

```json
{ "driven": { "governor": { "mode": "observe", "budgets": { "M": 5 }, "no_growth_turns": 60 } } }
```

A session that ends on a usage or rate limit after committing work is handed over as a `[partial]` draft pull request, like a stopped one; the task stays `rate_limited` and retryable.

**Version skew.** The server and the session image are deployed separately, so one runs ahead of the other for a while. The session reads `task.json`, and the server reads `session-usage.json`, `session-outcome.json` and `driven-report.json`, ignoring members they do not know: a field added on either side never stops a session.

### Turn limit, wall clock and continuations

A session has `max_turns` (assistant messages, default 80) and `max_minutes` (default 45) from the driven preset. A request can set both for one task: `driven.tasks[].max_turns` (1 to 1000) and `max_minutes` (1 to 480) replace the preset's for that task's sessions.

A session stopped by the turn limit or the wall clock does not lose its work (ADR 0044). The driver first commits the working tree to the task branch (`WIP: session stopped by <reason> after <n> turns`; nothing is committed when the tree is clean), then bundles the branch. If the bundle holds a commit past the base commit, chargehand starts another session container for the same task on the same branch name: the new session's workspace is the previous bundle, and its prompt is the goal plus a note that names the stop reason and tells it to read `git log` and the diff against the base, not redo finished work, finish, run the tests and print the report. The profile's `driven.limits.max_continuations` (default 2 when unset, 0 turns it off, at most 5; not in the preset, so Prompt CI is not involved) bounds how many follow; each gets `max_turns` and `max_minutes` again. The token cap (and the dollar cap with an API key) is the task's, not each session's: a continuation gets what the earlier sessions left, and none starts when nothing is left. Turns, tokens and dollars in events and in the task's outcome are summed over its sessions. Each continuation is a `container_started` event, `session container started (continuation 1 of 2, previous stopped by turn_limit)`. A stall for no progress or a repeated call, the token cap, and a question for a person (`needs_input`) never continue (a question is answered by a new batch, see [Answering a question](#answering-a-question)).

Files over 5 MiB and the image's tool caches (`.dotnet`, `.nuget`) are not committed by the snapshot; a snapshot that git could not make (a timeout, a live `index.lock`) is skipped and the partial pull request says so. A continuation that adds no commit beyond the one it was seeded with does not continue again, and one that cannot be started (the runner is at its container cap, the seed is refused, the call times out) leaves the task to the partial handover of the work so far. The handover scans every commit of the branch for secrets, not just the net diff.

A session that ends with a question (`needs_input`) after committing is handed over the same way, with its questions in the pull request body and the task detail, and stays `needs_input`. A task that ends without a finished report but with commits on its branch (the last allowed continuation also hit the limit, no progress, the token cap, a session error) is handed over as a **partial** draft pull request: the title starts `[partial] `, the body says the session was stopped, by what, and after how many turns, and that it is unfinished. chargehand still runs its own verification and records the result, but pushes and opens the draft even if the tests fail or time out, or the repository has no test command. A secret in the diff, CI-file changes and the other checks still refuse. The task stays `failed`, with `branch` and `pr_url` set and a detail such as `partial: stopped by turn_limit; draft PR opened`, so the batch summary stays honest. A stop with nothing committed is `failed` with no pull request, as before. The session image carries the driver: a new image digest is needed in `driven.images` for the snapshot and continuations to work.

`POST /v1/runs/{id}/cancel` cancels a run; `POST /v1/halt` cancels every run and refuses new ones until `POST /v1/resume`; `GET /v1/runs` lists runs with state, cost, branch and pull-request link. `chargehand runs kill --all` removes the containers by label with no server. Cancel never pushes. The cancelled batch's result says `cancelled`, not `tasks_incomplete`.

### Answering a question

A session that cannot go on without a person ends `needs_input`: the batch is `failed` with `tasks_incomplete`, the task's result is `needs_input` with the questions, and a `question` event carries them while the batch still runs. With commits on its branch, the task is also handed over as a `[partial]` draft pull request (above). The answer is a new batch with a task that continues the old one:

```json
{ "driven": { "tasks": [ { "id": "t1", "continue_from": { "run_id": "<the first batch's run id>", "task_id": "t1" }, "answers": ["Postgres", "Yes, keep the old API"] } ] },
  "context": { "preset": "driven", "repository": { "path": "...", "commit": "<the commit the first batch used>" } } }
```

The task needs no `goal` or `ref` (it takes the earlier task's) and starts from that task's kept work, on the same branch name: its first session is seeded with the kept bundle, as a continuation is (above). Its prompt is the earlier goal, the questions the session asked, your `answers` exactly as sent, a note about the commits already on the branch, and the earlier session's `progress.md` when it left one. `answers` is a list of strings with no pairing to the questions; write each so it stands alone. If the task asks again, continue from the new batch: the earlier rounds stay in the goal. The new batch's task is an ordinary task from then on (continuations, partial handover, the governor).

`continue_from` also takes a task that stopped with its work kept (a `[partial]` pull request after the turn limit, the token cap, a session error) and needs no `answers` then; the prompt says the earlier session was stopped before it finished. What counts is the `kept-work` artifact on the task's result (`branch`, `bundle_run`, `commits`, `base`), which exists whenever a task is handed over as partial. A task that asked a question before making any commit has no kept work: the new task starts from the base commit on a branch of its own, with the goal, questions and answers in the prompt.

The request is refused as `invalid_request` before anything starts when the earlier batch is not in the run log or has not finished, has no task with that id, the task completed or stopped with no work kept, it ended `needs_input` and the request gives no `answers`, or `context.repository.commit` is not the commit the earlier task started at (the kept branch is a series of commits on that base). `answers` without `continue_from`, `continue_from` with a `goal` or `ref`, and two tasks continuing the same one (they would push the same branch) are refused too. A kept bundle that is gone fails only that task, `invalid_request`.

**How long the work is kept.** A task's output volume (its bundle and handoff) is not removed when the task ends. The sweep at a server start removes every output volume that no running batch owns, except those of tasks that ended with kept work in the last 7 days (the task's last session and the one that holds its bundle). So work is continuable for at least 7 days; after that, the first restart removes it. A question asked before any commit keeps nothing but its goal and questions, which live in the run log. The pull request opened for the question is reused by the answering task's handover (the same branch); when that task finishes, the handover replaces its `[partial]` title and its body with the finished ones (a task that is partial again leaves them). If the host refuses the edit the push still stands and the `pr_opened` detail says the title could not be updated. Needs a session image from the release that added continuations (ADR 0044); no image change is needed for this step.

## Shared services

[ADR 0048](../adr/0048-shared-services-for-driven-sessions.md). Four things a repository's sessions share, so they stop probing the container and downloading cold.

**The environment note** needs no setting. Before its first turn a session reads a short block, appended to its prompt next to the static text: the tools the session image has (from `/opt/chargehand/environment.json`, written at image build by `chargehand session --probe`), the ones it lacks, that only the package allowlist answers and there is no Docker, the repository's detected ecosystems, the command chargehand will run on the branch (the request's `context.verify`, else the detected one), where the caches are and which test services exist. An image without the file is probed once by the driver. The block is not in the goal, so research and review calls do not carry it.

**Package caches** (`driven.services.caches`, a list of `nuget`, `npm`, `pip`, `gradle`, `maven`). One named volume per ecosystem and repository, `chargehand-cache-<ecosystem>-<12 hex>`, mounted read-write at `/cache/<ecosystem>` in that repository's sessions and in the verifier, with the package manager's variable pointed at it. Per repository, not shared: a session writes its cache while running the repository's own code, and a package manager trusts what is already in its cache, so a shared cache would let one repository choose what another builds. The volumes are not removed with a task or by the restart sweep and have no size limit; prune them by name (`docker volume ls -q -f name=chargehand-cache-`). They need a session image and a runner from the release that added them.

**Test services** (`driven.services.repositories`, per `owner/repo`, up to four). Each is a pinned image started on the batch's internal network before the first session and removed before the network, reachable as `name:port`, with its data directory in memory:

```json
"services": {
  "repositories": {
    "owner/repo": [
      { "name": "postgres", "image": "docker.io/library/postgres@sha256:<digest>", "port": 5432,
        "env": { "POSTGRES_PASSWORD": "test", "POSTGRES_DB": "app" }, "tmpfs": ["/var/lib/postgresql/data"],
        "note": "user postgres, password test, database app" }
    ]
  }
}
```

`env` holds test values for a container with no route out, never a real secret. The runner starts only images on its `--service-images`. A service may take a few seconds before it accepts connections (the note tells the session to retry); tasks of one repository in a batch share its services, so tests that need isolation use their own database names.

**A JDK image by ecosystem** (`driven.services.images`, `{"gradle": "<digest>", "maven": "<digest>"}`). A repository whose top level has that ecosystem gets that image for its sessions and its verification; the value must also be in `driven.images`. `images/session-jdk/Dockerfile` builds `FROM` the session image and adds a JDK, Gradle (checksum-verified) and Maven; the release workflow pushes it as `chargehand-session-jdk`. By hand: `docker build -f images/session-jdk/Dockerfile --build-arg BASE=<session image by digest> -t chargehand-session-jdk .`. It makes JVM Gradle and Maven repositories verifiable; it has no Android SDK. The Gradle and Maven package hosts are not in the driven preset's allowlist: add them under `driven.network.allow` (`chargehand init` lists them).

Not built yet: a code index of the base commit mounted read-only into sessions (decided in the ADR, deferred), a readiness wait for services, a size or age limit on cache volumes.

### Tasks that depend on each other

Independent tasks all start from the base commit. For work that builds on other work, give a task `depends_on`, a list of task ids of the same batch ([ADR 0049](../adr/0049-dependent-tasks-and-planning.md)):

```json
{ "driven": { "tasks": [
  { "id": "model",    "goal": "Add the Invoice model and its migration" },
  { "id": "endpoint", "goal": "Add GET /invoices on top of the model", "depends_on": ["model"] },
  { "id": "report",   "goal": "Add the monthly report", "depends_on": ["model", "endpoint"] } ] } }
```

A task starts when all its dependencies ended `completed`, whatever order the list is in; it holds no slot while it waits. If a dependency fails, asks a question or is cancelled, the task is `not_started` with `not started: the task it depends on, 'model', failed` (down the chain, with a `task_finished` event each). A `[partial]` task is `failed`, so it releases nothing.

The dependent's session starts from its dependencies' work. With one dependency, its branch is the dependent's starting point under the dependent's own name, and the draft pull request is opened against the dependency's branch, so it shows only the dependent's change (the body says so, and to merge the other first). If the host refuses that base, it is opened against the default branch and says so. With several, chargehand merges their branches into one, in the order listed, before any container starts; the pull request is against the default branch, and its diff includes theirs. A merge that conflicts fails the task as `merge_conflict`, naming the other task and up to 20 conflicting paths; nothing is started for it. The integrator leaves a task with dependencies alone. Unknown ids, a task depending on itself or twice on the same id, a cycle, and `depends_on` together with `continue_from` are refused as `invalid_request` before anything starts. A batch restart picks the chain up where it stood. The work a dependent starts from is what the dependency's last session left; commits the CI fixer added after it are not in it.

### Planning a batch

Off by default. `driven.planning.enabled` in the profile, or `driven.plan: true` on a request (`false` turns it off for one request), runs one cheap read-only run before the batch: the orchestrator on the `cheap` preset (`driven.planning.preset`), in the batch's repository at the base commit, recorded in the run log as a child of the batch. It costs a read-only run and is not part of the batch's caps. It does three things, and chargehand applies only what the rules below allow:

1. **Sizes** each task S, M or L for the governor's budget. A task with a `size` from the caller keeps it.
2. **Splits** a task it sizes L into 2 to 4 ordered parts, `t-1 → t-2 → … → t`: the last link keeps the id, the tracker reference and the tasks that depend on `t`, the first takes `t`'s own `depends_on`. Not split: a task with `size`, `budget_usd`, `max_turns` or `max_minutes` from the caller, one that continues another, or when the batch would pass 20 tasks.
3. **Assigns numbers** to tasks that would each take the next number of a sequence (migrations, ADR files): it reads the repository for the scheme and the latest number, and each task's goal gets `Plan: use migration number 0043 for this task...`. A value given twice stays with the first task.

The plan is the `plan` artifact of the batch result (what it checked, each task's size and where it came from, chains, assigned numbers, proposals it dropped and why, and `not_checked`) and a `plan` event. It never adds a dependency between your tasks. If the planner fails or answers with nothing usable, the batch runs as you sent it and the plan says `skipped` and why. Whether the tasks conflict in any way other than the numbers it assigned is not checked.

## The learning loop

Each task that ends leaves a record, so budgets and the governor's thresholds can be judged on what tasks cost instead of on a guess ([ADR 0045](../adr/0045-governed-sessions.md)). The server appends one line per task to `learning.jsonl`, next to the run log. A record holds counts, sizes, money and reasons, never a goal, a prompt or a session's text:

- **Where and what:** the batch and task ids, the account that started the batch (ADR 0050), the task's run id, the repository (`owner/name` of the remote, else the request's path), the size class (S, M or L) and where it came from (`caller`, `plan` for the planning step's estimate, or `default` for M when nothing named a size).
- **Budget:** the dollar-equivalent budget the governor held the task to and its source (`task` for the request's `budget_usd`, `flat` for the profile's or built-in budget of the size class; `none` with no governor).
- **Spend:** `usd_estimate` (the CI fix sessions' included; null when the profile has no prices), input, output, cache-read and cache-write tokens, turns, and how many continuation sessions ran.
- **Ending:** the outcome (`completed`, `partial` for work kept in a `[partial]` pull request, `failed`, `needs_input`), the last session's stop reason (`completed`, `turn_limit`, `checkpoint_spend`, `budget_spent`, ...), the governor's mode, a count per signal and action (and how many of those ended a session), and whether the test-integrity flag was raised.
- **Pull request:** its URL, number, repository on the forge, and the last commit chargehand put on the branch (the handover's, a CI fix's, or the head after a branch update chargehand made).

A task that threw before its session ended (cancelled, a start that failed) writes no record. A restart in the middle of the CI watch replaces the record written when the watch began, by run id, when the task ends.

**The human outcome of a pull request.** When the server starts and every `driven.learning.pr_check_minutes` (60) afterwards, it reads the pull request of every task that ended in the last `driven.learning.pr_days` days (14) and is not yet merged or closed, through the forge, read-only: `merged_unchanged` (the head at the merge is the commit chargehand last left), `merged_edited` (another head: a person added commits), `closed` (closed without a merge) or `open`. A line is written only when the outcome changes. It needs the forge credential that integration uses: the GitHub App for GitHub (`driven.integrator`), the forge token (`driven.forge.token_secret`, else the push credential) for GitLab. Without one, nothing is read and the outcomes stay empty. A squash or rebase merge is told from the pull request's own head, not from the commit on the base branch. A person who force-pushes the same commit back, or a forge that rewrites a head, shows as an edit; the check is run against a fake forge only.

**`chargehand learn report [--since 30d|<time>]`** and `GET /v1/learn?since=` (the API key is needed; an account's key sees only the tasks of its own batches, the owner's all) print a row per repository and size class: tasks, the median and 80th percentile of spend (nearest rank, over tasks whose spend is known), the completed and partial rates, the share of tasks with a governor checkpoint, how many of those still completed (a checkpointed task that completed is what a stop would have wrongly ended: the false-stop proxy ADR 0045 needs before `enforce`), and the share of resolved pull requests merged unchanged. `--since` takes a number of days or an ISO 8601 time. Small groups are noisy: the counts are in the table.

**The retro** is off by default (`driven.learning.retro`). When on, after a batch one read-only run on a cheap preset (`driven.learning.retro_preset`, `cheap`), recorded in the run log as a child of the batch, is given that batch's records (sizes, budgets, spend, stop reasons, governor counts) and writes at most 12 lines: what cost more than its budget, which signals fired, whether the sizes look right, one or two changes to try. It is the batch result's `retro` artifact (`status` `written` or `skipped` and why, `run_id`, `tasks`, `text`), costs a read-only run outside the batch's caps, is a model's advice that can be wrong, and never changes the batch's status. The prompt is in code, not under `prompts/`, so Prompt CI has nothing new to gate. **Not built:** filing the retro to a tracker's inbox. chargehand has no write path to a tracker yet (a task source only reads), so `IRetroSink` is the hook: a deployment that implements it gets each written retro, and one that throws is ignored. A sink (or a notifier like it) is the next extension point.

## Try it end to end

`scripts/driven-e2e.sh` runs the whole path against a real model, by hand, never in CI. It needs Docker, the .NET SDK, python3, `claude` on `PATH` at the version inside the session image, a session image pushed to a registry (build `images/session/Dockerfile`; the profile takes the image by digest), and an Anthropic API key with a **low spend limit set in the console**:

```bash
export CHARGEHAND_E2E_MODEL_KEY=<capped key>
export CHARGEHAND_E2E_IMAGE=<registry>/<image>@sha256:<digest>
scripts/driven-e2e.sh
```

It builds a synthetic repository with a local bare remote that refuses every branch except `chargehand/*`, starts its own server on port 4390 with a throwaway profile (`driven.enabled` true, `max_parallel` 2, the key read from the environment and never written to a file) and a stub of the GitHub endpoint that opens draft pull requests, then runs three tasks: one easy, one that must implement a function and remove a test's skip, and one that cannot pass. It checks that two draft pull requests were recorded, one task failed, the batch ended `failed` with `tasks_incomplete`, the default branch did not move, a cancelled task leaves no container and no pull request, and neither the push token nor the model key appears in any file the run made. The task that cannot pass is two contradictory tests; a model that edits them has dodged it, and the script then fails `impossible_tests_untouched` (it diffs the branch against the base for test files). `CHARGEHAND_E2E_REPO=node` swaps the Python repository for a small Node one (`node --test`) with the same three tasks, and `CHARGEHAND_E2E_TASKS=<file>` replaces the tasks with a JSON list of `{id, goal}` (the default stays Python). `CHARGEHAND_E2E_REPO=<path of a git checkout>` runs on a real repository instead: the script clones its committed history (no untracked files, no hooks), makes its current branch `main` of the local remote and never touches the checkout's own remote; it then needs `CHARGEHAND_E2E_TASKS` and `CHARGEHAND_E2E_VERIFY`, the verification command as a JSON argument vector (for a Node project with dependencies, `["sh","-c","npm ci && scripts/check.sh"]`; the registries the preset allows are reachable through the egress container). `CHARGEHAND_E2E_RUNNER=runner` or `proxy` runs the batch the way a VPS deploys it: the throwaway server talks to a real `chargehand runner` process with the deployment's policy flags (source root, the callback forward), and in `proxy` mode the runner reaches docker through a `docker-socket-proxy` container started with the deployment's image and flags; a case asserts the proxy served the batch. The first VPS batch found four defects on that path that the default `direct` mode cannot show. It does not show a Linux-only one: a Mac's bind mounts hide the owner of a checkout. The environment variables are listed at the top of the script. Two switches in the CLI make the local remote and the stub possible and exist for this script only (`CHARGEHAND_E2E_GITHUB_API`, `CHARGEHAND_E2E_LOCAL_REMOTE`); they are not profile keys.

With `CHARGEHAND_E2E_STREAMS=<dir>` the script copies each task's stored session stream (`stream.jsonl`, secrets redacted) out of its output volume and runs `chargehand runs adherence <dir>/*.jsonl`, which reports per session whether research, a write, a test run and a review came in that order with at most 2 fix rounds, and whether at least 7 of 10 sessions did (fewer than 10 is reported as not conclusive). It prints two numbers: `adherence` (the sessions that followed) and `honest_stop` (sessions that did research, a write and a test run in order, made no review and edited no test file: a task that could not be done and was stopped with a reason). `honest_stop` is not counted in the 7 of 10 bar. Ten sessions means running the script until ten streams are collected, for example the three tasks over four runs, or the plan's five tasks twice; point the helper at the combined directory. The cancel case waits for the task's own container before it cancels, then allows 20 seconds for no container to be left.

## The model credential

How the credential reaches a session is recorded on the batch result as `credential_delivery`:

| Profile | Delivery | Where the real credential is |
|---|---|---|
| `claude_code.oauth_token_secret` (the subscription) | `token_exchange` | only the batch's egress container. Its model endpoint accepts a per-task token (signed with a key made for the batch, bound to the run, its token cap and an expiry) and swaps in the real token toward `api.anthropic.com`; a session gets the token as `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_BASE_URL` pointing at the endpoint. The runner service passes the credential to the egress container's env file and forwards only to `api.anthropic.com`. |
| `api_key_secret` with `driven.network.model_url` | `gateway_key` | at the operator's gateway; a session holds the key it issued (next section) |
| `api_key_secret` alone | `environment` | the session container's environment |

**Measured (2026-10-10), token exchange.** `scripts/driven-e2e.sh` on the subscription with `CHARGEHAND_E2E_RUNNER=proxy` (a real `chargehand runner` behind a socket proxy, the VPS's path) and a session image built from this change: one task on the Python repository, `completed` in a draft pull request, 5,496 input plus output tokens, every case ok, including that no sampled session container's environment held the real token, that the session's calls went through the egress container's model endpoint, the cancel case and the credential scan. One task, one synthetic repository, a local remote. API-key mode is not sent through the exchange: it is not measured there.

## The model credential through a gateway

By default the real model credential is in the session container's environment (`credential_delivery: environment` on the batch result), where hostile repository code could read it. With `driven.network.model_url` set, the session gets instead the key an Anthropic-compatible gateway issued for driven sessions, with a budget, a model list and revocation at the gateway, and `ANTHROPIC_BASE_URL` pointing at it (`credential_delivery: gateway_key`). The key is `claude_code.api_key_secret` (priced mode: a subscription token cannot be used through a gateway, and the dollar cap binds live), and it is among the values the diff scan looks for.

```json
"claude_code": { "version": "2.1.283", "api_key_secret": "chargehand-driven-gateway-key" },
"driven": { "network": { "model_url": "http://gateway-host:4001/anthropic" } }
```

An `http` URL is reached through a second forward on the batch's egress container (the proxy answers CONNECT to port 443 only), so its port must differ from `mcp_forward`'s; the session sees `http://chargehand-driven:<port>/anthropic`. An `https` URL goes through the proxy and its host joins the allowlist. A URL with credentials or a query, or one used with a subscription token, is refused before anything is created. The server's own workers (the research and review a session asks for) use the same key, so set `claude_code.base_url` to a URL the server reaches the gateway at. The gateway must name its host: a forward target is refused when it is an address literal. What the gateway must accept (the header the key travels in, the model ids Claude Code sends, the `anthropic-beta` header) is the operator's to verify; Bifrost's `sk-bf-` keys travel in `x-api-key`, which Claude Code sends.

**Measured (2026-10-10).** `scripts/driven-e2e.sh` with `CHARGEHAND_E2E_MODEL_URL` set to a Bifrost gateway (a virtual key limited to Anthropic models, 20 USD a month, sent as `x-api-key`; session image 0.8.4, Claude Code 2.1.283, local OrbStack): one task on the Python repository ended `completed` in a draft pull request on the local remote, `credential_delivery: gateway_key`, 2,837 input plus output tokens, 0.17 USD, every case ok including the cancel case and the credential scan. The first attempt failed on an address-literal forward target and the second ended `needs_input` because the server's research worker had no `claude_code.base_url`; both are the notes above. One task, one synthetic repository, a local remote.

## Configure it

The profile's `driven` block (`schemas` and `profiles/profile.schema.json` document each key): `enabled` (default false), `max_parallel`, `max_parallel_total`, `max_session_calls` (research and review runs executing at once across all sessions, default 2: with more sessions than slots, sessions wait on each other), `images` (by digest), `network.allow`, `limits` (see "Limits and the kill switch"), `runner` (URL and the secret item for its key), `push_secret`, `integrator` (merge by policy and fix failing CI as a GitHub App, "Merging by policy" above), `forge` (GitLab or GitHub Enterprise: the kind, an API root and the GitLab token, "GitLab" above), `planning` (`enabled`, `preset`; off by default, "Planning a batch" above), `learning` (`retro`, `retro_preset`, `pr_days`, `pr_check_minutes`; records are always written, the retro is off by default, "The learning loop" above), and `task_source` (how a tracker item id becomes a goal through a mapped MCP tool), and `services` (package caches, test services and a session image by ecosystem, "Shared services" above). `network.outside` and `network.mcp_forward` (`host:port` of the chargehand server as the egress container reaches it) let a session call chargehand for research and review. `network.otlp_url` turns on Claude Code's own telemetry (above). `images[0]` is the session image and the egress image. Keep `enabled` false in any shared profile. A request adds `driven: { tasks: [{id, ref | goal, max_turns?, max_minutes?, size?, depends_on?}], plan?, max_parallel, max_tokens_total | max_usd_total }` and `context.repository`.

`chargehand init <repo>` writes a starter `driven` block with the package hosts that repository needs in `network.allow`, and `chargehand doctor` checks the images, the runner, the secrets and that `network.allow` covers the repositories under `repository_roots` ([reference](reference.md#commands)).
