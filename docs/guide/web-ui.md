The server can serve a small web page at `/ui/` ([ADR 0054](../adr/0054-web-ui.md)). It is for watching and for the few actions you would otherwise do with `curl`. It calls the routes in [the server guide](server.md) and nothing else, so what an account may see and do there is what it may do over HTTP.

A new operator console is being built at `/console/` to replace it ([ADR 0056](../adr/0056-operator-console.md), [below](#the-operator-console-console)). It has the design system, the shell, Overview, Needs you, Start a batch, Analytics and Learning so far; everything on this page up to that section describes `/ui/`, which stays until the console reaches parity.

## Turn it on

It is off unless the profile asks:

```json
{ "http": { "port": 4300, "api_key_secret": "chargehand-api-key", "ui": true } }
```

Restart `chargehand serve`; its start line then ends `UI /ui/, console /console/` (the one setting turns on both). Open `http://127.0.0.1:4300/ui/` (the same `allowed_hosts` rules apply as for the API). The page's files are public and load without a key; every call the page makes carries one.

## Sign in

Paste an API key: the owner's `http.api_key_secret` or an account's `chk1.<id>.<secret>` ([accounts](server.md#accounts-and-named-keys)). The page checks it with `GET /v1/accounts/me`. A wrong key shows an error and nothing is stored. **Sign out** removes the key. There is no server-side session.

For everyday watching, sign in with an account key. The owner's key can also halt the server.

Behind Cloudflare Access with `http.cloudflare_access` set, the console (not `/ui/`) asks for nothing: it signs in as the account your Access email maps to, and **Sign out** also ends the Access session ([server guide](server.md#sign-in-by-cloudflare-access-identity), [ADR 0071](../adr/0071-sign-in-by-cloudflare-access-identity.md)).

### Where the key is kept, and what that costs

The key is kept in `sessionStorage`: it lives in that tab, is gone when the tab closes, and is never sent anywhere but the server that served the page, as `Authorization: Bearer ...`. It is not a cookie, so nothing sends it by itself and there is nothing for a forged request to ride on. It is not `localStorage`, so it does not outlive the tab or reach other tabs.

The trade-off is that a script running in the page could read it. The page is built so none can: every response under `/ui/` carries `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, which allows no inline script, no `eval` and no other origin; results, claims, branch names and diffs reach the page only as text (the code never builds markup from a string); a link appears only for an `http` or `https` URL; and there is no third-party code and no build step. Over plain HTTP on a private network the key crosses the network in clear, as it does for any API caller ([ADR 0024](../adr/0024-server-on-a-private-network-and-release-images.md)): put TLS in front when that matters.

## Screens

**Runs** (`#/`) lists runs, newest first, 100 at most, refreshed every 5 seconds (untick Auto-refresh to stop it). Columns: start time, run id, state, kind (`single`, or `batch` for a request with a `driven` block), preset, repository, the account (owner only), cost, tokens, branch and pull request link. Cost is the result's priced `usd`; a subscription run has none and shows a dash. Filters: state, kind, repository (exact path) and, for the owner, actor. A batch's research and review calls are runs of their own; they are hidden unless you tick "Show session calls". Above the list is **Spend**.

**Spend** shows the account's spend in the UTC day and month against its caps (`max_usd_per_day`, `max_usd_per_month`, `max_tokens_per_day`, `max_tokens_per_month`), when each window resets, and its unfinished runs against `max_concurrent_runs`. A cap that is not set says "no cap". The figures come from `GET /v1/accounts/me`, the same spend a new request is checked against, so a refusal with `budget_exceeded` matches what the page shows. The owner has no caps; its spend is that of runs recorded as `owner`.

**Run** (`#/runs/<id>`) shows the run's state and, while it is unfinished, the **live events**: `accepted`, `started`, `intake`, `node_started`, `node_finished`, and for a batch `container_started`, `session_progress` (stage, turns, tokens and `usd_estimate`, the session's dollar equivalent so far), `pushed`, `pr_opened`, `task_finished`, `governor`, `integrated` and the rest. A batch also gets a live table of its tasks. The page reads the stream with `fetch`, because the browser's own server-sent-events client cannot send a bearer header. When the run finishes, the result replaces the stream. A run that another process holds, or a server that restarted, is polled every few seconds instead.

The result shows the summary, the error and what to do about it, confidence, usage, and:

- **Claims** with their support verdict and confidence. Each citation is a link to `path:line` at the commit when the repository has a web address: taken from a pull request link in the result (`github.com/.../pull/N`, GitLab `.../-/merge_requests/N`), or typed once into the box the page offers and kept in this browser's `localStorage` (it is not a secret). A `file` citation uses the evidence's `commit`, else the run's commit; a `url` citation links to the URL; the rest are shown as text. With no web address, citations are text.
- **Tasks** for a batch: state, tokens, cost, branch, pull request link, error code and detail; each task id links to the task's own run.
- **Artifacts**, each collapsed: `changes` (changed paths with their line counts and the diff), `verification`, `plan`, `pull-request`, `branch`, `review`, `session-log` and `governor-log` (references, with their hash), and any other kind as inline text.

**Cancel run** asks, then calls `POST /v1/runs/{id}/cancel`; the run ends `failed` with `cancelled`. It answers `409` for a run another process holds.

**Start a run** (`#/new`) sends `POST /v1/runs` with `Prefer: wait=0` and goes to the new run's page. Fields: goal (`text`), preset (the presets the server has), repository path and commit (`context.repository`; most presets need both), and for accounts allowed `driven`, "Run as a batch" with a list of tasks (id, goal, size, `depends_on`), which sets preset `driven`. A refusal (`400` bad request, `403` driven or repository not allowed, `429` cap or concurrency) is shown with the server's message.

**Learning** (`#/learn`) shows `GET /v1/learn`: per repository and size class, finished tasks, completion and partial rates, the median and 80th-percentile spend, the share that hit a checkpoint, pull requests and the share merged unchanged ([the learning loop](driven.md#the-learning-loop)). Choose 7, 30 or 90 days or all time. An account sees only its own batches.

**Halt server** and **Resume server** appear for the owner in the header and call `POST /v1/halt` and `/v1/resume`; a halted server shows a banner to everyone.

## What the server adds for it

- `GET /v1/accounts/me`: the caller's `name`, `owner`, `driven`, `repositories`, `limits`, `spend.day` and `spend.month` (`usd`, `tokens`, `resets_at`), `unfinished_runs`, `halted` and `presets`. A run token gets `403`, as on every route it does not open.
- `GET /v1/runs` accepts `kind=single|batch`, `repository=<exact path>`, `run_id=` and, for the owner, `actor=`; an account always gets its own runs.
- `run-summary/v1` gains optional `kind`, `repository`, `commit` and `tokens` (additive).

## Not tested in CI (`/ui/`)

The tests cover what a .NET test can see: the files are served only when `http.ui` is on, without a key, with the policy and the other headers; every other route still needs a key; the embedded files are the folder's; no file names another origin, builds markup from a string, carries inline script or style, or calls `fetch` outside `api.js`; `/v1/accounts/me` and the new list filters. The JavaScript itself was exercised by hand in a browser against a server with seeded runs; nothing runs it automatically.

## The operator console (`/console/`)

The console is a single-page app in `web/console/` built with Vite: React and TypeScript, TanStack Router and Query, Vitest, Playwright and Biome ([ADR 0056](../adr/0056-operator-console.md) says why a build step now, and why these). The server embeds the build and serves it at `/console/` under the same `http.ui` setting as `/ui/`, with the same rules: the files are public and need no key; you paste an API key, it stays in `sessionStorage` for the tab and goes out as the bearer header; every response carries the policy `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, so no inline script or style and no other origin. Signing out, or a `401`, drops the key and everything fetched with it.

Files under `assets/` carry a content hash and are cached for a year; `index.html` is never cached. A path under `/console/` that is not a file and has no file extension (`/console/runs/<id>`) gets `index.html`, so a reload or a pasted link opens the same screen; a missing file is a `404`.

**What is there now.** The shell, sign-in, and every screen.

- **Shell.** A left rail (collapsible with `[`) on a desktop, a bottom tab bar on a phone (Overview, Needs you with its count, Runs, Start, More), a top bar with the screen's name, the live state with the time in Kyiv, ⌘K, theme, row density and an account menu (who is signed in, today's spend, Sign out). A banner says when the server is halted (the owner can resume from it) or when new starts are paused by a rate limit. The rail leaves out the screens an account may not call (`intake`, `accounts`, `system` answer `403`).
- **Overview** (`/console/`): sessions against the limit, spend today, what needs you, merges in the last 24 hours; the batches running now with a progress bar by task state, slots, tokens and spend against the batch's cap; a summary of Needs you; spend today against each account's cap (an account with no cap shows "no cap" on a dashed track); what admission looks at (the host's free memory with its reserve, load, session slots, the rate-limit pause); the halt switch, which asks first and says what stops; the server's version, uptime and runner; recent merges. It reads `GET /v1/overview`, `/v1/inbox`, `/v1/runs?kind=batch`, `/v1/batches/{id}`, `/v1/pulls` and, for the owner, `/v1/system`. An account sees its own runs and spend and nothing about the host or other accounts.
- **Needs you** (`/console/needs-you`): the inbox as cards, questions first. A question carries the request that answers it: type the answer and **Answer and continue** sends `POST /v1/runs` with a driven task that continues the asking one (`continue_from`, `answers`, the repository and preset the item named), with `Prefer: wait=0`; the card then links the new batch. A pull request shows what it waits for (policy `ask`, a test-integrity flag, a `[partial]` draft) and links to it (only an `http` or `https` address is ever a link). A failure shows its error code, what happened and the next step. Filter by kind; `j` and `k` move the cursor, `Enter` opens the task, `a` goes to the answer box. **Dismiss** on a card, or **Dismiss all shown** for the filter in view, takes items out of the inbox for everyone who sees them (`POST /v1/inbox/dismiss`); the notice that follows has **Undo**. A card marked `×N` stands for N identical failures, and the line under the title counts what left on its own (superseded by a later run, an infrastructure failure a later run outlived, a question a batch continued), what was dismissed and the duplicates folded ([ADR 0064](../adr/0064-inbox-items-resolve-on-their-own-or-are-dismissed.md)). The server has no route to merge a pull request or retry a task, so those two actions are not offered.
- **Start a batch** (`/console/new`): the composer for a driven batch. It takes a preset (the owner's batch presets from `GET /v1/system`, an account's from `GET /v1/accounts/me`), a repository from `GET /v1/repositories` with the commit filled from the checkout's HEAD, a label, and the tasks: an id, a size (Auto, S, M, L), an optional budget, a multi-line goal and the tasks it waits for. Tasks can be added, removed and moved; a dependency that would close a loop is not offered. **Import tasks** reads pasted text (a line per task, where `[S]`, `(L)` or `M:` before the goal sets the size) or a JSON list. Options are planning (on, off, or the server's default), `max_parallel`, the token cap and the dollar cap; pull requests are always drafts. A layered graph draws `depends_on`. The estimate gives each task the budget the server will choose when it starts (its own `budget_usd`, else p80 of past tasks of its size in this repository once there are 20, else the same across repositories, else the flat S, M or L budget) and says which one it used and how many past tasks stand behind it; the history is `GET /v1/learn` over 60 days, and for the owner the profile's own thresholds replace the defaults. The checks mirror `schemas/request/v1`, the rules the server adds (unique ids, 1 to 20 tasks, `depends_on` naming tasks of the batch with no loop, a cap of tokens or dollars) and what the account may do; each shows at its field, and "not filled in yet" stays quiet until a start is tried. The JSON view is the same request as text: JSON that parses fills the form, and fields the form has no control for (`ref`, `max_turns`, `continue_from`, ...) are kept and sent. **Templates** keep named forms, without their commit, in this browser's `localStorage`. **Start batch** sends `POST /v1/runs` with `Prefer: wait=0` and opens the new run; a refusal shows its status and code and keeps the form. Another screen opens the form filled in through the router's state (`cloneAsNewBatch` in `screens/start/prefill.ts`); no screen does yet. GitHub issues cannot be imported: the server has no route that lists them.
- **Analytics** (`/console/analytics`): what finished tasks cost and how they ended, over time. It reads `GET /v1/analytics` (the learning records bucketed by day, week or month and grouped by repository, size class or, for the owner, account) and `GET /v1/learn`. Four figures (spend as the dollar equivalent of the tokens, pass rate with its 95% Wilson interval, the governor's false-stop proxy, pull requests merged), then spend and tokens stacked by the grouping (eight hues at most, the tail folded into a grey "Other"; a group keeps its hue when a filter drops its neighbour), the cache-read share of input, pass rate by repository and size, the wall time of finished batches (from `GET /v1/runs?kind=batch`: the analytics route has no per-task duration), each size class's p80 spend against the budget a task of that size was last held to, the governor's false-stop rate per mode against the 5% line of [ADR 0045](../adr/0045-governed-sessions.md), tasks that went on in a fresh session against those that did not, and pull requests merged by how. A range (7, 30, 90 days, all), a bucket and a grouping choose what is asked. Time series are drawn by uPlot on a canvas; the small charts are SVG. Hover or focus a mark and it shows its value and the route and field it is read from; **Show data** under each chart is the same numbers as a table. Nothing is estimated: a bucket with no task is a zero, one with no input is a gap, a rate over few tasks shows its wide interval and its counts. What the server does not record is listed at the bottom: the CI fixer's attempts (a task's spend includes its fix sessions), and a benchmark comparison, which is left out because no route serves `chargehand bench` results.
- **Learning** (`/console/learning`): what past tasks cost and the budgets chargehand derives from them. A table of every repository and size class from `GET /v1/learn` (tasks, median and p80 spend, completed, partial, checkpoint, "then done" (checkpointed tasks that still completed: the false-stop proxy) and "merged as is") with how each group's budget is chosen: the task's own budget, else the p80 of the same size class in its repository when `min_tasks` finished in `window_days`, else the same over all repositories, else the flat budget. The numbers come from `driven.governor.history` when the owner's key can read `GET /v1/system`, and the documented defaults say so otherwise. **Budgets in force** reads the latest finished batches (`GET /v1/batches/{id}`) for the budget of the newest task of each size class and where it came from (`p80 of 23 past tasks, this repository`). **Retros** shows the `retro` of those batches (`driven.learning.retro`, off by default), labelled as a model's advice and always as text. **Lessons** are not stored by the server: they are rules over the table (a size class that rarely completes, checkpoints that were wrong, pull requests people rewrite, too little history), each with the counts it stands on and the route it is read from, at most two of a kind.
- **Notices.** The console polls the inbox and the batch runs and, when something new needs you (a task asks a question, a pull request waits, a task or run fails, a batch finishes or fails), raises a notice on the page. When you turn browser notifications on (a button asks the browser once) and the page is in the background, the same event is also a browser notification with the same title. They need a secure page (https, or localhost); on plain http nothing is asked and the page's own notices still appear. Each kind can be switched off on Needs you.
- **Runs** (`/console/runs`): every run the caller sees, newest first, in a table that draws only the rows in view (a phone gets cards). The server narrows what it can (one state, kind, repository, account and a start time, `GET /v1/runs?status=&kind=&repository=&actor=&since=`); search, preset and the states the server has no word for (needs attention, cancelled) are applied to the runs already loaded, and the list asks for the next 100 (at most 500: there is no cursor) while a search finds too few. Choose a built-in view or save the current filters as a view (kept in this browser's `localStorage`). Select runs, then **Cancel** asks first and sends `POST /v1/runs/{id}/cancel` for each run that is running; the finished ones are skipped and counted. `j` and `k` move a cursor, `x` selects, `Enter` opens, `/` searches.
- **Batch** (`/console/runs/<id>`, a run of kind `batch`): the header (state, repository at its commit, account, start, time elapsed, **Cancel batch** which asks first, **Halt server** for the owner), tokens and dollars against the batch's caps, and eight tabs, the open one in the address (`?tab=`). **Tasks**: the task graph (`depends_on` edges, laid out by ELK, each node a button) and a table with state, stage, tokens, spend against budget, pull request and time. **Timeline**: a bar per session in parallel slots, a dashed edge for a continuation, a band for a rate-limit pause. **Events**: the recorded events and the live stream (`GET /v1/runs/{id}/events`) as one list, by kind and by task, with Pause. **Governor**: mode, decisions as the server keeps them (counts per signal and rung), and the budget each task was held to. **Spend**: tokens (input, output, cache read and write) and the dollar equivalent per task, and the cache's share. **Pull requests**: the integrator's policy, the last thing it said and what it waits for. **Artifacts**: the batch's result and plan, and each task's changes (a diff with syntax colour), verification run and references. **Request**: the request rebuilt from the batch view, **Copy JSON**, and **Clone as a new batch**, which opens Start a batch with the request carried in the router's state. The tabs say what the server does not keep (`not_recorded`) where they would otherwise look complete.
- **Task** (a drawer over the batch, `?task=<id>`, or a page at `/console/runs/<batch>/tasks/<task>`; a phone always gets the page): the whole goal, size, budget and where it came from, spend against it, dependencies, sessions and continuations, branch, pull request, chargehand's verification run beside the session's own claim, the test-integrity flag, the changes with the diff, and the task's events. A task that asked a question shows it with one box per question and **Answer and continue**, which sends the request the server carried (`POST /v1/runs`, `continue_from`, `answers`), as Needs you does.
- **Research** (`/console/runs/<id>`, a run that is not a batch): the summary, each claim with its support check and confidence, and each citation as `path:line` that links to the file at the commit once the repository's web address is known (from a pull request link, or typed once and kept in this browser); open questions; confidence and usage; and the signature, shown and said to be unchecked, because the console has no key to check it with.

**Keys.** `⌘K` (or `Ctrl+K`) opens the palette: go to a screen, open a run or a task (find a run by the six hex digits at the end of its id), or run an action; halt appears there but asks first. `?` lists the keys that work. `g` then `o`, `n`, `r`, `s` or `a` goes to Overview, Needs you, Runs, Start or Analytics; `[` collapses the rail; `/` focuses a screen's filter when it has one; `Esc` closes a layer. Cancel and halt have no bare key.

**Look.** The design system is the one approved on 13 October 2026: dark first (a lime accent that means "your move"), light second, system fonts, no emoji. A browser that asks for light gets light until you choose; theme, row density (compact, default, comfortable), the rail's width and the notice switches are kept in this browser's `localStorage` and nowhere else.

### Where a screen's code goes

A screen lives in `web/console/src/screens/<name>/` (its component, its `model.ts` of pure functions, its CSS and its test) and is registered in two places: its route in `src/router.tsx` (replace the `placeholder(...)` line) and, if it is new, its entry in `src/shell/screens.ts`, which feeds the rail, the tab bar, the palette and the `g` keys. Shared parts are `src/ui/` (the design system's 18 components as React, one file each, all exported from `src/ui/index.ts`), `src/api/` (one file per contract: its types, its query options and its hook; `answer.ts` sends an answer), `src/lib/` (formats, status words, safe links) and `src/shell/` (layout, palette, hotkeys, notices, preferences). A new shortcut adds a row to `src/shell/shortcuts.ts`, so the `?` sheet never lists a key that does nothing. `src/testing/` holds the fixtures of every contract (invented data, times relative to now) and a fake server for Vitest; `e2e/mock.ts` answers the same fixtures in the browser for Playwright.

Rules the code keeps: a colour, size or space comes from `tokens.css`, never a literal; every state of a list or panel (loading, empty, error with the failing call and a Retry, long content) is built; a modal layer is `Dialog` (the native `<dialog>`), never a library that injects a style element; style is set through the style object model (`cssVars`), never an inline style attribute; user-supplied text reaches the page only as text, and a link is built only from an `http` or `https` address.

### Build and develop

Needs Node 24 (`web/console/.nvmrc`; `engines` allows newer).

```bash
cd web/console
npm ci --ignore-scripts      # from the lockfile, no install scripts (.npmrc says the same)
npm run dev                  # Vite on :5173; /v1 is proxied to CHARGEHAND_URL (default http://127.0.0.1:4300)
npm run tokens               # regenerate src/styles/tokens.css from design/tokens.json (the build and a test fail when it is stale)
npm run lint                 # Biome: lint and format check (npm run format fixes)
npm run typecheck            # tsc --noEmit
npm test                     # Vitest
npm run build                # vite build, then scripts/verify-dist.mjs
npm run test:e2e             # Playwright smoke test against `vite preview` (needs: npx playwright install chromium)
```

The dev server has no Content-Security-Policy (Vite's hot reload needs inline script); `vite preview` and the server do. After `npm run build`, `dotnet build` embeds `web/console/dist`. **A build without it still works:** the .NET tests do not need Node, and `/console/` answers `503` with a short page that says the console is not built. `scripts/check.sh` runs the web steps when Node is installed, and prints that it skipped them when it is not (the smoke test too, when Chromium for Playwright is missing); CI always runs them.

### Supply chain

Versions are exact in `package.json`, the lockfile is committed, installs run with `--ignore-scripts`, and `.npmrc` sets `min-release-age=14`, so no package younger than 14 days is resolved; Dependabot proposes updates weekly (minor and patch together) with a 14-day cooldown. There is no CDN: every script, style and font comes from the build. The Docker image builds the console in its own Node stage, so Node and the packages are not in the image.

### How it is tested

Vitest covers the design system's tokens (the committed `tokens.css` is what `design/tokens.json` generates, dark is the default and light is both a choice and a browser's, the bundle's stylesheet names no property the tokens lack), the formats of the design system (tokens as `48.2k`, dollars as `≈ $6.20`, durations, Kyiv time), each of the 18 primitives (classes, roles, states, keyboard), the shell (rail, top bar, palette, `g` keys, `?` sheet, phone tab bar, theme and density, focus), the notices (a new inbox item or finished batch raises one notice, once; browser notifications only when allowed, on a secure page and while the page is in the background), the API client (the bearer header, a `401` dropping the key, error bodies), the server-sent-events parser, the key store, and the screens against a fake server: every state (data, loading, error with and without older data, empty, long content, halted, paused, an account's view), the answer a question sends, and, for Start a batch, the request it builds (its model: the checks against the schema's limits, cycles, the estimate and the JSON round trip, apart from React); for Analytics and Learning, the arithmetic apart from React (buckets and the axis, stacks and their hues, rates and Wilson intervals, bins, the budget rule, retros, lessons), the scales of the charts, the options handed to uPlot, and that no chart or screen file holds a literal colour. The Playwright tests serve the built app with `vite preview`, which sends the server's policy, answer the API in the browser, and run the shell, Overview, Needs you, Start a batch, Analytics and Learning at 1280 and 375 px in the dark and the light theme (the palette, the shortcuts, the halt dialog and the More sheet too), each with axe-core (`@axe-core/playwright`): no serious or critical violation is allowed. Every one fails on a console error, an uncaught error, a policy violation or a request to another origin, and checks there is no sideways scroll and that a phone's targets are 44 px. `CONSOLE_SHOTS=<dir> npm run test:e2e` also saves a screenshot of each look; `CONSOLE_E2E_PORT=<port>` runs the preview server on another port (default 4173; `scripts/check.sh` picks a free one unless it is set), since Playwright reuses a server already on the port. A chart's canvas is checked to hold painted pixels, and that uPlot adds no style element. The .NET tests check what the server does with the build: served only when `http.ui` is on, without a key, with the policy and the other headers, hashed assets cached and the page not, client routes falling back to `index.html`, a missing asset a `404`, the embedded files equal to `dist`, and that `web/console/csp.ts` holds the same policy.
